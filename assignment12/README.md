# 과제 12 — 퀵 정렬의 피벗 선택에 따른 성능 비교

## 1. 과제 목적

동일한 무작위 정수 배열에 퀵 정렬(Quick Sort)의 세 가지 피벗 선택 방식을 적용하고, **데이터 값 간 비교 횟수**를 측정한다. 피벗 선택 방식 외에는 동일한 분할 알고리즘을 사용하여 성능 차이의 원인을 분석한다. 보너스로 **재귀적 퀵 정렬**과 명시적 **스택을 사용하는 반복적 퀵 정렬**의 실행시간을 비교한다.

## 2. 파일 및 실행 방법

- `main.c`: 데이터 생성, 세 가지 피벗 방식, 비교 횟수 측정, 정렬 검증 및 보너스 실험
- `README.md`: 실험 조건, 실제 실행 결과와 비교·분석

macOS/Linux의 GCC 또는 Clang:

```bash
gcc -std=c11 -O2 -Wall -Wextra -Wpedantic main.c -o main
./main
```

Windows의 MinGW GCC:

```powershell
gcc -std=c11 -O2 -Wall -Wextra -Wpedantic main.c -o main.exe
.\main.exe
```

별도 라이브러리 및 외부 데이터 파일 없이 실행된다.

**데이터 시드 사용 방식:** 데이터 크기가 달라져도 `DATA_SEED`에서 새로 시작하므로 큰 배열은 작은 배열과 같은 난수 수열의 앞부분을 공유한다. 단, 각 크기 안에서는 세 방법이 완전히 **같은 값과 같은 순서**의 원본 복사본으로 정렬을 시작한다. 재현성을 위해 무작위 피벗에도 별도의 고정 `PIVOT_SEED`(`20261212`)를 사용하고, 분할할 때마다 현재 구간의 난수 위치를 다시 선택한다.

### 3.1. 피벗 선택 방식

1. **First Element:** 현재 구간의 첫 번째 원소를 피벗으로 사용한다.
2. **Random Pivot:** 현재 구간의 임의 위치를 매 분할 단계에서 새로 선택한다. 난수 생성 자체는 값 비교로 세지 않는다.
3. **Median-of-Three:** 첫 번째·가운데·마지막 원소 중 값의 중앙값을 피벗으로 사용한다. **산술평균이 아닌 중앙값**이며, 중앙값 판별에 사용한 값 비교 2~3회도 합산한다.

각 경우에 선택한 피벗을 현재 구간의 마지막 원소와 교환한 다음, **완전히 같은 Lomuto 분할 함수**를 호출한다. 그러므로 피벗을 고르는 부분만 다르고 나머지 분할·재귀 처리 과정은 동일하다. `<=` 비교 조건으로 피벗과 같은 중복 값도 처리한다.

### 4.1. 데이터 크기 증가에 따른 비교 횟수 변화

데이터가 커질수록 세 방식 모두 비교 횟수가 증가하였다. `n=1,000`에서 `n=20,000`으로 데이터가 **20배** 증가할 때 비교 횟수는 First가 약 **28.7배**, Random이 약 **33.3배**, Median-3가 약 **30.4배** 증가했다. 단순한 선형 증가보다 가파르지만, 무작위 데이터에 대한 일반적인 퀵 정렬의 평균 복잡도 **O(n log n)** 경향과 부합한다. 이는 제한된 크기에서 확인한 실험 경향이며, 최악의 경우 O(n²)가 발생하지 않는다는 의미는 아니다.

### 4.2. 피벗 선택 방식별 성능 차이

- **First:** 구현이 간단하고 피벗 선택 시 값 비교가 필요 없다. 이번 데이터에서는 `n=4,000`에서 최소 비교 횟수를 기록했다. 하지만 피벗이 최솟값 또는 최댓값에 가까우면 분할이 심하게 불균형해져 비교 횟수가 크게 늘 수 있다.
- **Random:** 매 분할에서 임의 위치의 원소를 사용하므로 특정 입력 순서로 인한 일관된 최악 분할의 위험을 확률적으로 줄인다. `n=2,000`에서 가장 적게 비교했지만, `n=20,000`에서는 세 방법 중 가장 많았다. 무작위 선택이 **각 분할의 균형을 보장하지는 않기 때문**이다.
- **Median-of-Three:** 양 끝과 가운데 값을 비교하여 비교적 극단적인 피벗 선택을 피하려는 방식이다. **6개 크기 중 4개**에서 최소 비교 횟수를 기록했다. `n=20,000`의 317,620회는 First의 329,878회보다 약 **3.7%**, Random의 356,007회보다 약 **10.8%** 적었다. 중앙값을 선택하는 **추가 비교 비용을 이미 포함**한 결과이다.

### 4.3. 분할 결과가 비교 횟수에 영향을 미치는 이유

Lomuto 분할에서 길이가 `m`인 구간은 피벗 이외의 `m-1`개 원소를 피벗과 비교한다. 피벗이 중간 크기 부근이면 양쪽 부분 배열의 크기가 비슷해져, 다음 단계에서 처리하는 구간들의 총 비교 횟수가 상대적으로 작아진다. 반대로 피벗이 계속 최솟값·최댓값에 가깝다면 한쪽 구간이 거의 비지 않아 비교를 반복하게 되므로 **최악 O(n²)**까지 증가할 수 있다.

Median-of-Three는 추가로 2~3회의 선택 비교를 수행하지만, 더 균형 잡힌 분할로 절약하는 비교가 그 비용보다 클 수 있다. 다만 세 위치의 값만 확인하므로 진짜 전체 구간의 중앙값은 아니다. 또한 본 구현의 `<=` 분할 조건에서는 피벗과 **같은 값이 많이 반복**될 경우 한쪽으로 몰려 불균형이 생길 수 있다. 따라서 세 피벗 방식 중 어느 하나가 항상 최소 비교를 보장하지 않는다.

### 4.4. 필수 실험 결론

이번 실험에서는 **Median-of-Three가 전반적으로 가장 효과적**이었다. 특히 큰 데이터 크기 `8,000`, `16,000`, `20,000`에서 모두 비교 횟수가 가장 적었다. 그 이유는 추가적인 피벗 선택 비교를 감수하더라도 상대적으로 균형 잡힌 분할을 얻어 후속 재귀 구간의 비교를 줄였기 때문으로 해석할 수 있다. 다만 입력의 난수 시드, 데이터 분포, 중복 정도에 따라 결과는 달라질 수 있으므로 **모든 입력에 대한 절대적 우위**로 일반화할 수는 없다.

## 5. 보너스 — 재귀적 vs 반복적 퀵 정렬

### 5.1. 비교 조건 및 방법

- 원본 데이터: 크기 **10,000**, 필수 실험과 같은 의사난수 생성 방식
- 피벗 선택: 양쪽 모두 **Median-of-Three**
- 분할: 양쪽 모두 **동일한 Lomuto partition**
- 구현: 재귀 호출로 구간 처리 vs `Range {left, right}`를 저장하는 **명시적 스택**으로 구간 처리
- 측정: 각각 **200회** 정렬하고 1회 평균 **CPU 시간(ms)**을 측정 (`clock()` 사용)
- 시간 측정에 **포함**: 퀵 정렬 함수 내부 실행 (반복적 구현이 사용하는 스택의 할당·해제 포함)
- 시간 측정에서 **제외**: 데이터 생성, 원본 배열 복사, 정렬 결과 검증, 결과 출력
- 정렬 결과 및 값 비교 횟수 일치 검증 (두 방식 모두 **146,538회**)

### 5.2. 실제 실행 결과

```text
[Bonus: Recursive vs Iterative]
Data Size            : 10000
Pivot                : Median-of-Three
Repeated Runs        : 200 (average CPU time)
Recursive Quick Sort : 1.097670 ms
Iterative Quick Sort : 0.971455 ms

```

위 결과는 한 실행 환경의 측정값이다. **반복적 방법이 이 측정에서는 약 11.5% 빨랐지만**, 시스템 부하, 컴파일러, 최적화, 메모리 상태에 따라 실행시간 차이와 순위가 바뀔 수 있다. 특히 차이가 약 0.13ms로 작아서 반복 측정이나 실행 환경을 달리한 추가 측정 없이 일반적인 우열을 확정하기는 어렵다.

### 5.3. 실행시간 차이가 발생하는 이유

두 구현은 같은 배열에 같은 피벗과 분할을 적용하여 **데이터 값 비교 횟수가 정확히 일치**한다. 따라서 시간 차이가 난다면 비교할 원소의 수 때문이 아니라 **구간을 관리하는 방식의 오버헤드** 때문이다.

- **재귀적 구현:** 재귀 함수 호출, 복귀 및 호출 스택 프레임을 사용한다. 깊이가 커질수록 호출 부담과 스택 사용량이 늘 수 있다.
- **반복적 구현:** 함수를 매번 재귀 호출하지 않고 `while` 반복문과 배열 기반의 명시적 스택으로 구간을 관리한다. 대신 스택을 위한 메모리 할당·해제 및 push/pop 연산이 추가된다.
- **공통점:** 피벗과 분할이 같으므로 평균적인 정렬 복잡도는 모두 **O(n log n)**, 최악 시간복잡도는 **O(n²)**이다. 메모리 사용 방식은 서로 다르며, 본 반복적 구현은 최악의 경우를 대비해 `n`개 구간을 저장할 수 있는 공간을 할당한다.

이번 실험에서는 반복적 구현이 조금 빨랐으나 차이는 작았다. 따라서 **호출 오버헤드 감소가 유리하게 작용했을 가능성**이 있으며, 반복적 구현의 스택 연산·할당 비용과 컴파일러 최적화의 영향도 함께 고려해야 한다.
