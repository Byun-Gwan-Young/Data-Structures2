# 과제 14 — 힙 정렬, 퀵 정렬 및 병합 정렬의 성능 비교

## 1. 과제 목적 및 제출물

과제 13에서 사용한 **같은 데이터 생성과 기존 Merge Sort / Quick Sort(First, Random, Median-of-Three) 코드**를 유지하고, **입력 배열을 그대로 사용하는 Max Heap Sort**를 추가한다. 동일한 원본 데이터로 5가지 정렬 방법의 **데이터 값 비교 횟수, 평균 실행시간, 최대 추가 메모리**를 측정·비교한다.

제출 파일은 **`main.c`와 `README.md`** 두 개다. 외부 라이브러리, 별도 데이터 파일, `sample_output.txt`는 필요하지 않다.

### 컴파일 및 실행

macOS(이번 Mac 실험과 동일한 컴파일 명령, 최적화 옵션 미지정):

```bash
gcc main.c -o main
./main
```

## 3. 알고리즘 구현 및 숫자 비교 횟수

### 3.1. 힙 정렬(Heap Sort) — 이번 과제에서 추가

1. 별도 힙 배열 없이 **원래 입력 배열 안에서 최대 힙(Max Heap)**을 만든다. `n / 2 - 1`번 인덱스부터 0번까지 **상향식(bottom-up) heapify**를 수행한다.
2. 루트 `array[0]`의 최댓값을 현재 힙의 마지막 요소와 교환해 정렬된 뒤쪽 구간으로 보낸다.
3. 힙 범위를 하나 줄인 다음 루트에서 **반복문 기반 sift-down**으로 최대 힙 속성을 복구한다. 힙이 빌 때까지 반복한다.
4. `heap_sift_down()`은 왼쪽 자식과 현재 최대값을 비교할 때 1회, 오른쪽 자식이 있을 경우 다시 비교할 때 1회를 측정한다. **초기 힙 구성과 최댓값 추출 후 힙 복구의 비교를 모두 합산**한다.

힙 정렬은 데이터 전체 크기에 비례하는 동적 보조 배열을 할당하지 않는다. 재귀 함수 없이 반복적으로 sift-down을 수행하므로 이 구현의 추가 공간은 **`O(1)`**이다.

### 3.2. 병합 정렬(Merge Sort) — 과제 13 유지

배열을 재귀적으로 절반씩 분할하고 정렬된 구간을 병합한다. 병합 과정에서 **`array[i] <= array[j]`**가 평가될 때마다 1회 비교로 센다. 한쪽 구간이 소진된 후 나머지 값을 그대로 복사하는 부분은 값 비교가 없으므로 제외한다. 정렬 함수 안에서 임시 배열 `n * sizeof(int)`을 동적 할당해 사용하고 해제한다.

### 3.3. 퀵 정렬(Quick Sort) — 과제 13 유지

세 방식 모두 기존 **Lomuto 분할**을 사용하며, 선택한 피벗을 오른쪽 끝으로 옮긴 후 분할한다.

- **First Element:** 현재 구간의 첫 번째 값을 피벗으로 선택한다. 피벗 선택 자체에는 값 비교가 없다.
- **Random Pivot:** 고정된 피벗 시드의 `xorshift32` 난수로 구간 안의 피벗 위치를 선택한다. 난수 생성과 인덱스 선택은 값 비교가 아니다.
- **Median-of-Three:** 첫 번째·가운데·마지막 값 중 중앙값을 피벗으로 선택하며, 이때 실제 일어나는 **2~3회의 데이터 값 비교도 합산**한다.

모든 Quick 방식에서 분할 과정의 **`array[scan] <= pivot_value`**를 값 비교로 센다. 피벗 선택법 외의 분할 및 재귀 호출 로직은 동일하다.

**공통 계수 규칙:** 오직 정수 **데이터 값끼리 비교한 연산**만 측정한다. 반복문의 인덱스 검사, 배열 범위 검사, 정렬 종료 조건, 복사, 스왑, 난수 생성, 정렬 결과 검증은 비교 횟수에 포함하지 않는다.

## 4. 실행시간 및 메모리 계산 기준

### 4.1. 실행시간

C 표준의 **`clock()`**을 사용한다. 함수 호출 **직전**에 `start=clock()`, 정렬 함수가 끝난 **직후**에 `end=clock()`을 취득하고, `(end-start) * 1000 / CLOCKS_PER_SEC`를 계산한다. 동일한 원본 복사본으로 총 100회 반복한 후 평균 CPU 시간(ms)을 출력한다.

- 시간 측정 **포함:** 정렬 함수 내부의 값 비교·스왑·배열 이동·재귀 호출·임시 메모리 할당 및 해제(병합 정렬).
- 시간 측정 **제외:** 데이터 생성, `memcpy()` 입력 복사, `qsort()` 참조 결과 생성, 오름차순·참조 결과 검증, 콘솔 출력.
- 각 방법에 동일한 API와 단위를 사용한다. `clock()`은 **CPU 시간**이며 실제 경과시간(wall time)이 아니다. 짧은 수행 시간은 측정 환경의 영향을 받으므로 미세한 차이를 절대적인 우열로 해석하지 않는다.

### 4.2. 최대 추가 메모리 사용량(Byte)

**실제 OS 메모리 사용량(RSS) 실측이 아니라, `sizeof` 기반의 소스 수준 스택 프레임 모델 + 정렬 함수 내부 동적 배열 크기를 합산한 최대 동시 사용량의 계산값**이다. 소스의 `update_peak()`는 매 정렬의 보조공간 후보 중 최대값을 기록한다.

- **Heap Sort:** `sizeof(HeapRootFrame) + sizeof(HeapSiftFrame)`이 힙 복구 중 동시에 필요하다. 이 구현은 반복형이므로 깊이가 증가하지 않고, 별도 힙 저장 배열도 없다. 첫 호출 이전에는 루트 프레임만 고려한다.
- **Merge Sort:** `n * sizeof(int) + sizeof(MergeRootFrame) + (재귀 깊이 × sizeof(MergeRecursiveFrame)) + (병합 중에만 sizeof(MergeCombineFrame))`의 수행 중 최댓값.
- **Quick Sort:** `sizeof(QuickRootFrame) + (재귀 깊이 × sizeof(QuickRecursiveFrame)) + (분할 시 sizeof(QuickPartitionFrame) + sizeof(QuickSelectFrame) + Median3일 경우 sizeof(QuickMedianFrame))`의 수행 중 최댓값.

동시에 실행되는 프레임만 합산한다. 원본 배열·입력 작업 배열·검증용 배열(`qsort` 결과)·공통 통계 객체·실험용 루프는 **정렬 알고리즘 고유의 추가 공간이 아니므로 제외**한다. `malloc` 메타데이터, ABI 복귀 주소, 레지스터 저장, 컴파일러 최적화/인라인의 실제 스택 효과 등도 이 **추정 모델에는 포함하지 않는다**. 따라서 계산값이 OS가 관측하는 실제 물리 메모리와 일치한다고 볼 수 없다.

이번 실행에서 출력된 **64비트 환경의 `sizeof` 모델**은 다음과 같다.

| 스택 프레임 모델 | Byte |
|---|---:|
| Heap root / sift | 32 / 40 |
| Merge root / recursive / combine | 32 / 40 / 48 |
| Quick root / recursive / partition / select / median | 32 / 40 / 56 / 40 / 32 |

힙 정렬은 최대 **72B(32+40)**, 병합 정렬은 `n × 4B` 임시 배열 때문에 **O(n)**, 퀵 정렬은 재귀 깊이에 따라 **평균적인 무작위 입력 O(log n), 최악 O(n)**의 추가 스택 공간을 갖는다. 위 수치는 프레임 추정에 기반하므로 32/64비트 및 플랫폼 차이에 따라 달라질 수 있다.

## 6. 실험 결과 분석 (Mac 실측 기반)

### 6.1. 데이터 크기 증가에 따른 숫자 비교 횟수

- **Heap Sort:** `n=1,000`에서 **16,862회** → `n=20,000`에서 **510,808회**, 약 **30.3배**로 증가했다. 상향식 최대 힙 구성은 `O(n)`이고 이후 최댓값 추출마다 힙 속성 복구를 수행하므로 전체적으로 `O(n log n)`에 해당한다. 부모와 왼쪽·오른쪽 자식의 값을 비교하는 sift-down 과정이 반복된다.
- **Merge Sort:** **8,720회 → 260,824회**, 약 **29.9배**로 늘었다. 정렬된 두 부분의 앞쪽 값만 비교하면서 병합하므로 **6개 크기 모두에서 비교 횟수가 가장 적었다.** 분할 단계 수가 로그에 비례하고 각 단계에서 전체 원소를 병합하여 `O(n log n)` 경향을 보인다.
- **Quick (First):** **11,491회 → 329,878회**, 약 **28.7배**; **Quick (Random):** **10,687회 → 356,007회**, 약 **33.3배**; **Quick (Median3):** **10,446회 → 317,620회**, 약 **30.4배**이다. 피벗의 분할 균형이 달라지므로 비교 횟수가 동일하지 않다. Median3은 피벗 선택을 위한 2~3회의 데이터 값 비교까지 계산한 수치이다.

입력 원소 수가 **20배**로 증가하는 동안 비교 횟수는 대략 **29~33배**가 되었고, 이는 이번 무작위 입력에서 다섯 방식이 전반적으로 `n log n`에 가까운 증가를 보였음을 나타낸다. `n=20,000`에서 Heap의 비교 횟수(510,808회)는 Merge(260,824회)의 약 **1.96배**였다. 비교 횟수가 실제 소요시간을 전부 결정하지는 않으며, 값 이동·메모리 접근·재귀 호출 등의 비용도 작용한다.

### 6.2. 힙·병합·퀵 정렬의 실행시간 차이

- `n=1,000`: **Heap 0.106110ms, Merge 0.091100ms, Quick First 0.074440ms, Random 0.081440ms, Median3 0.068840ms**였다. 이 크기에서는 **Quick Median3**가 가장 짧은 시간을 기록했다.
- `n=2,000`: **Heap 0.187150ms, Merge 0.167860ms, Quick First 0.137950ms, Random 0.155430ms, Median3 0.143340ms**였다. 이 크기부터 `n=20,000`까지는 **Quick First가 각 크기에서 가장 짧은 시간**을 기록했다.
- `n=20,000`: **Heap 2.377170ms, Merge 2.147490ms, Quick First 1.821510ms, Random 2.005260ms, Median3 1.877480ms**였다. Heap은 Merge보다 약 **10.7%**, Quick First보다 약 **30.5%** 오래 걸렸다(각 비교 대상의 소요시간을 분모로 계산).

**모든 6개 입력 크기에서 Heap이 Merge보다 느렸다.** Heap은 추가 배열을 사용하지 않지만, 각 최댓값 추출 후 트리를 따라 내려가며 자식 값 비교 및 교환을 반복한다. 이 과정에서 인덱스가 떨어진 곳에 접근하는 패턴과 상대적으로 높은 비교 횟수가 실행시간에 영향을 줄 수 있다. Merge는 데이터 값 비교가 가장 적지만 임시 배열 할당·해제 및 병합 중 복사 비용이 있다. Quick은 현재 무작위 데이터에서 비교적 적은 재귀 깊이와 제자리 분할의 이점을 보였지만, 피벗 선택 비용과 교환 횟수도 실행시간에 반영된다.

**증가 추세:** `n=1,000 → 20,000`에서 Heap의 시간은 **약 22.4배**(0.106110→2.377170ms), Merge는 **약 23.6배**(0.091100→2.147490ms), Quick First는 **약 24.5배**(0.074440→1.821510ms) 늘었다. 이 결과는 입력 크기가 증가하면 세 정렬 모두 시간이 증가함을 보여주지만, 실행시간 자체는 컴파일러·CPU 부하·캐시·실행 순서 등 환경 요인에 의존한다. 특히 수십 마이크로초 수준의 차이로 보편적 성능 순위를 단정할 수 없다.

### 6.3. 추가 메모리 사용량 비교

- **Heap Sort:** 모든 크기에서 **72B**. `HeapRootFrame(32B) + HeapSiftFrame(40B)`의 최대 동시 사용량을 계산하였다. 입력 배열 자체에 최대 힙을 만들고 **반복형 sift-down**을 수행하므로 추가 공간은 `O(1)`이다.
- **Merge Sort:** `n=1,000`에서 **4,480B**, `n=20,000`에서 **80,680B**. 마지막 크기에서는 `20,000 × sizeof(int)=80,000B` 임시 배열과 **680B**의 프레임 모델 공간을 합산하였다. 입력에 비례하는 보조 배열 때문에 `O(n)`이다.
- **Quick Sort:** `n=20,000`에서 **First 1,368B / Random 1,568B / Median3 1,200B**였다. 입력 크기가 늘 때에도 프레임 수는 단순히 같은 비율로 늘지 않고, 매 실행에서 발생한 재귀 깊이와 피벗 분할 균형에 따라 달라진다. 일반적인 무작위 입력의 평균 스택 공간은 `O(log n)`이나, 한쪽 분할이 반복되면 최악 `O(n)`이다.

`n=20,000`에서 Merge의 추가 공간 계산값(80,680B)은 Heap(72B)의 **약 1,121배**다. 단, 이 Byte는 **OS 메모리 실측이 아니라 `sizeof` 기반 소스 수준 최대 동시 프레임 + 임시 배열 모델**의 추정값이다. 함수 인라이닝과 실제 스택 배치, 할당자 메타데이터 등은 계산에 포함되지 않는다. 원본 입력과 모든 알고리즘에 공통으로 필요한 실험 배열도 제외하였다.

### 6.4. 퀵 정렬 피벗 선택 방식의 영향

- **First Element:** `n=20,000`에서 **329,878회 / 1.821510ms / 1,368B**였다. 해당 크기에서 Quick 3종 중 **실행시간은 가장 짧았지만**, 비교 횟수는 Median3보다 많았다. 피벗 선택 시 추가 데이터 비교가 없지만, 이미 정렬된 입력에서 극단값을 계속 고르면 최악 `O(n²)`로 악화될 수 있다.
- **Random Pivot:** 같은 크기에서 **356,007회 / 2.005260ms / 1,568B**. 이번 데이터에서 Quick 3종 중 비교 횟수와 실행시간이 가장 컸다. 난수 기반 선택은 특정 위치에 편중되는 위험을 줄이지만 매번 균형 분할을 보장하지 않으며 난수 생성 비용도 든다.
- **Median-of-Three:** 같은 크기에서 **317,620회 / 1.877480ms / 1,200B**. Quick 3종 중 **비교 횟수와 계산상 추가 메모리가 가장 작았다.** 세 값의 중앙값을 선택하는 추가 비교까지 포함했는데도 비교 횟수가 적었다. 다만 실제 실행시간은 First보다 약 **3.1% 길었다.**

`n=20,000`에서 Median3의 값 비교 횟수는 Random보다 **약 10.8% 적었다.** 그렇지만 `n=2,000`에서는 Random이 Median3보다 비교 횟수가 적고, `n=4,000`에서는 First가 가장 적었다. 즉 **이번 실험에서도 피벗 선택법의 우열이 모든 크기에서 일관되지는 않았다.** 중복값이 매우 많거나 모든 값이 같은 경우 현재 `<=` 조건의 **2-way Lomuto 분할**은 한쪽 분할로 쏠릴 수 있으며, 세 방법 모두 최악 `O(n²)` 가능성이 있다.

### 6.5. 시간 복잡도 및 공간 복잡도

| 알고리즘 | 최선 시간 | 평균 시간 | 최악 시간 | 추가 공간(현재 구현) |
|---|---|---|---|---|
| Heap Sort | `O(n log n)` | `O(n log n)` | `O(n log n)` | **`O(1)`** — 별도 힙 배열 없음, 반복형 sift-down |
| Merge Sort | `O(n log n)` | `O(n log n)` | `O(n log n)` | **`O(n)`** — 임시 배열 + `O(log n)` 재귀 프레임 |
| Quick (First) | `O(n log n)` | 무작위 순열 평균 `O(n log n)` | `O(n²)` | 무작위 순열 평균 `O(log n)`, 최악 `O(n)` |
| Quick (Random) | `O(n log n)` | 피벗 선택에 대한 기대 `O(n log n)`* | `O(n²)` | 기대 `O(log n)`*, 최악 `O(n)` |
| Quick (Median3) | `O(n log n)` | 일반적인 무작위 입력에서 `O(n log n)` | `O(n²)` | 일반적인 무작위 입력에서 `O(log n)`, 최악 `O(n)` |

*Random Pivot의 기대 복잡도는 값의 중복으로 분할이 심하게 편향되지 않는 상황을 전제한다. 이번 코드는 `<=`를 쓰는 2-way Lomuto 분할이므로, 예를 들어 **모든 값이 동일한 입력에서는 세 Quick 방식 모두 `O(n²)` 시간과 `O(n)` 재귀 스택**이 될 수 있다. 현재 코드는 두 분할 구간을 각각 재귀 호출하므로 꼬리 재귀 제거나 작은 쪽만 재귀 호출하는 추가 최적화는 사용하지 않는다.

### 6.6. 실험 결론

사용자 Mac 실측에서 **값 비교 횟수는 모든 크기에서 Merge Sort가 최소**, **추가 메모리 계산값은 Heap Sort가 최소**였다. Heap은 최대 힙을 계속 복구하면서 값 비교·교환을 수행하지만, 입력 배열 자체를 이용해 **72B의 상수 추가 공간**만 기록했다. Merge는 비교 횟수가 적고 분할이 균형적이지만 입력 크기에 비례하는 **임시 배열 사용**으로 메모리가 커졌다. Quick은 무작위 입력에서 실행시간이 유리했으나 피벗에 따라 분할 균형과 스택 깊이, 비교 횟수가 달랐다.

`n=20,000` 실측 결과는 **Heap 510,808회 / 2.377170ms / 72B**, **Merge 260,824회 / 2.147490ms / 80,680B**, **Quick First 329,878회 / 1.821510ms / 1,368B**, **Quick Random 356,007회 / 2.005260ms / 1,568B**, **Quick Median3 317,620회 / 1.877480ms / 1,200B**였다. 이번 실험에서 Quick First는 가장 짧은 평균 CPU 시간을 기록했고, Median3은 Quick 방식 중 가장 적은 비교 횟수를 기록했다. 다만 특정 시드와 한 장비에서 관찰한 속도 순위를 모든 데이터에 일반화할 수는 없다.

> **참고:** 이 README의 시간은 **2026-11-12 사용자 Mac에서 `gcc main.c -o main`로 빌드하여 직접 실행한 값**이다. 컴파일 옵션이나 환경을 바꿔 실행하면 평균 CPU 시간은 달라질 수 있다. 고정된 데이터/피벗 시드·동일한 `int` 크기에서 비교 횟수는 같아야 하고, 계산상 메모리는 플랫폼의 구조체 `sizeof`에 따라 달라질 수 있다.
