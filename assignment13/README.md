# 과제 13 — 병합 정렬과 퀵 정렬의 성능 비교

## 1. 과제 목적

동일한 무작위 정수 데이터에 **병합 정렬(Merge Sort)**과 **퀵 정렬(Quick Sort: First / Random / Median-of-Three)**을 적용하여 **숫자 비교 횟수·실행시간·최대 추가 메모리 사용량**을 비교한다. 데이터 생성 및 퀵 정렬의 피벗·분할 로직은 과제 12와 동일하게 유지하고, 병합 정렬을 추가하였다.

## 2. 제출 파일 및 실행 방법

제출 파일은 **`main.c`, `README.md` 두 개**다. 별도 데이터 파일이나 외부 라이브러리는 필요하지 않다.

macOS / Linux 터미널:

```bash
gcc -std=c11 -O2 -Wall -Wextra -Wpedantic main.c -o main
./main
```

Windows(MinGW GCC):

```powershell
gcc -std=c11 -O2 -Wall -Wextra -Wpedantic main.c -o main.exe
.\main.exe
```

프로그램은 모든 데이터 크기와 알고리즘의 실험을 수행하고, 결과 검증이 끝나면 `Verification: PASS`를 출력한다. 실패 시 오류 메시지를 표준 오류로 출력하고 비정상 종료한다.

## 3. 실험 조건

| 항목 | 조건 |
|---|---|
| 언어 | C11 |
| 데이터 크기 | `1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000` |
| 데이터 생성 | 과제 12와 동일한 **xorshift32**, `DATA_SEED=20261103` |
| 데이터 범위 | `0~99,999`의 정수. 중복 허용 |
| 피벗 난수 | 과제 12와 동일한 `PIVOT_SEED=20261212`, 매 크기에서 `PIVOT_SEED ^ n`으로 초기화 |
| 입력 조건 | 각 크기에서 원본을 **1회 생성**, 4개 알고리즘에 정렬 전 `memcpy`하여 동일한 데이터 순서 보장 |
| 정렬 방식 | 모두 오름차순 |
| 퀵 정렬 분할 | 과제 12와 동일한 **Lomuto partition**, `array[scan] <= pivot` |
| 실행시간 | 각 알고리즘을 **100회** 동일한 원본 복사본으로 반복 실행한 **1회 평균 CPU 시간(ms)** |
| 정확성 검증 | 매 회차마다 오름차순 검사와 C 표준 `qsort`로 구한 참조 정렬 결과와의 원소별 일치 검사 |
| 메모리 | 원본 및 정렬 대상 입력 배열 제외. 정렬 중에 필요한 **최대 추가 메모리의 계산값(Byte)** |

각 `n`에서는 데이터 생성기의 초기 상태를 동일하게 재설정하므로, 큰 데이터는 작은 데이터와 같은 의사난수 수열의 앞부분을 공유한다. 다만 동일 크기 안의 4개 정렬 알고리즘은 **완전히 동일한 배열을 복사받아** 사용한다. 무작위 피벗도 고정 시드를 사용하기 때문에 비교 횟수와 아래 메모리 계산값은 반복 실행 시 재현된다.

## 4. 알고리즘 및 측정 기준

### 4.1. 병합 정렬

- 배열을 가운데에서 두 부분으로 분할하고, 각각을 재귀적으로 정렬한 다음 두 정렬된 구간을 병합한다.
- **병합 중 `array[i] <= array[j]`**가 실제 평가될 때마다 숫자 비교 횟수를 1 증가시킨다.
- 어느 한쪽 구간이 소진되어 남은 원소를 옮길 때는 **데이터 값 간 비교가 없으므로** 추가로 세지 않는다.
- 임시 배열 `n * sizeof(int)` Byte를 정렬 함수 안에서 `malloc`하고, 정렬이 끝나면 `free`한다. 이 할당·해제도 실행시간에 포함한다.

### 4.2. 퀵 정렬

- **First Element**: 구간의 첫 번째 값을 피벗으로 선택.
- **Random Pivot**: 구간에서 새 난수 위치를 선택해 피벗으로 사용. 난수 생성 자체는 값 비교가 아니므로 제외.
- **Median-of-Three**: 구간의 첫 번째·가운데·마지막 세 **값의 중앙값**을 피벗으로 선택. 해당 선택 과정의 값 비교 2~3회도 전체 비교 횟수에 포함.
- 선택한 피벗을 마지막 위치로 옮겨 **동일한 Lomuto 분할**을 수행한다. 분할 중 `array[scan] <= pivot_value` 비교마다 1을 더한다.
- 피벗 선택 방식만 달리하고 나머지 분할·재귀 구현은 동일하다.

**공통 카운팅 규칙:** 실제 정수 **값 대 값** 비교만 센다. `i < n`, `left >= right`, `i <= middle` 같은 인덱스·종료 조건 검사, 스왑, 복사, 난수 발생은 제외한다.

### 4.3. 실행시간

C 표준 `clock()`으로 정렬 함수 호출 **직전부터 직후까지**의 CPU 시간을 구한다. `((end - start) / CLOCKS_PER_SEC) * 1000`을 ms로 환산하며, 각 정렬 알고리즘에 **같은 방법**을 적용한다. 원본 생성·입력 배열 복사·정렬 결과 검증·출력은 측정 구간 밖이다. 정렬 함수 안에서 사용하는 메모리 할당·해제와 비교 횟수 기록은 측정 구간에 포함된다.

각 알고리즘의 시간을 100회 측정해 **평균**을 출력한다. 짧은 실행을 단 한 번 측정했을 때 발생하는 시간 해상도 및 외부 시스템 부하의 영향을 줄이기 위한 방식이다. `clock()`은 벽시계가 아니라 **프로세스 CPU 시간**이므로 스케줄링이나 다른 컴파일 환경에 따라 결과가 달라질 수 있다.

### 4.4. 최대 추가 메모리 계산 방식

**실제 OS 메모리 프로파일링이 아니라, `sizeof`로 구한 소스 수준의 스택 프레임 모델과 정렬용 동적 할당량을 조합한 최대 동시 사용량 추정이다.** 코드의 `update_peak()`가 정렬 도중 나타나는 최대 합계를 기록한다. 원본 데이터 및 복사하여 정렬하는 **입력 배열 자체**, 검증용 `qsort` 배열, 계측 결과를 저장하는 공통 통계 객체는 제외했다.

- **병합 정렬**: `n * sizeof(int)`(임시 배열) `+ sizeof(MergeRootFrame)`(최상위 함수 모델) `+ 재귀 깊이 × sizeof(MergeRecursiveFrame)` `+ (병합 도중에만 sizeof(MergeCombineFrame))`. 매 재귀 호출 진입 및 병합 직전에 계산한 후보 중 최대값 사용.
- **퀵 정렬**: `sizeof(QuickRootFrame)` `+ 재귀 깊이 × sizeof(QuickRecursiveFrame)` `+ (분할 도중 sizeof(QuickPartitionFrame) + sizeof(QuickSelectFrame) + Median-of-Three라면 sizeof(QuickMedianFrame))`. 매 재귀 호출 진입 및 피벗 선택·분할 시점에서 계산한 후보 중 최대값 사용.
- 재귀 깊이는 진행 중인 재귀 호출 개수를 의미하며, 종료되는 자식 호출까지 포함된다. 새 구간으로 들어갈 때마다 1씩 증가시켜 기록한다.
- 배열의 동적 메모리는 할당 요청 크기만 포함한다. **`malloc` 내부 관리 오버헤드, C ABI의 실제 복귀 주소·레지스터 저장·컴파일러 최적화에 따른 실제 프레임 크기, 인라인 가능한 소형 헬퍼의 별도 프레임 등은 포함되지 않는다.** 따라서 수치는 실제 프로세스 RSS 또는 물리적 스택 메모리의 정밀 실측값이 아니라, **모든 알고리즘에 동일한 원칙을 적용한 계산 추정치**다.

이번 실행 환경(64비트)에서 `sizeof`로 확인한 프레임 모델 크기는 다음과 같다.

| 프레임 모델 | 크기(Byte) |
|---|---:|
| `MergeRootFrame` | 32 |
| `MergeRecursiveFrame` | 40 |
| `MergeCombineFrame` | 48 |
| `QuickRootFrame` | 32 |
| `QuickRecursiveFrame` | 40 |
| `QuickPartitionFrame` | 56 |
| `QuickSelectFrame` | 40 |
| `QuickMedianFrame` | 32 |

즉, 병합 정렬에서 대부분의 추가 메모리는 `n * 4` Byte 임시 배열이 차지하고, 퀵 정렬에서는 깊이에 비례하는 호출 스택이 대부분을 차지한다. 컴파일러·플랫폼·32/64비트 차이에 따라 `sizeof`가 바뀌면 메모리 출력도 달라질 수 있다.

## 6. 실험 결과 분석

### 6.1. 데이터 크기에 따른 비교 횟수 변화

- `n=1,000`에서 `n=20,000`으로 입력이 **20배** 늘었을 때 병합 정렬의 비교는 **8,720 → 260,824회(약 29.9배)**가 되었다.
- 같은 구간에서 퀵 정렬의 비교는 **First: 11,491 → 329,878회(약 28.7배)**, **Random: 10,687 → 356,007회(약 33.3배)**, **Median-of-Three: 10,446 → 317,620회(약 30.4배)**였다.
- 네 방식 모두 데이터 크기에 비례한 단순 선형 증가보다 가파르지만, 무작위 데이터에서 예상하는 **`O(n log n)`**의 증가 경향을 보였다.
- 병합 정렬은 항상 두 부분으로 거의 반씩 나누므로 병합 전체 단계 수가 예측 가능하다. 반면 퀵 정렬은 피벗이 분할 비율을 결정하므로 비교 횟수가 입력 분포와 피벗 방식에 따라 달라진다.
- 이번 입력에서는 **모든 6개 크기에서 병합 정렬이 최소 비교 횟수**를 기록했다. 특히 `n=20,000`에서 병합 정렬의 비교 260,824회는 퀵 정렬 중 비교가 가장 적은 Median-of-Three 317,620회보다 **약 17.9% 적었다**. 그렇다고 병합 정렬이 모든 입력에서 반드시 비교가 적은 것은 아니다.

### 6.2. 실행시간 차이 및 동작 방식

- `n=1,000`: 병합 **0.022840ms**, First **0.013180ms**, Random **0.017330ms**, Median-of-Three **0.011650ms**. 이 측정에서는 Median-of-Three가 가장 빨랐다.
- `n=20,000`: 병합 **1.639120ms**, First **0.994440ms**, Random **1.129020ms**, Median-of-Three **1.033780ms**. 병합 정렬보다 세 퀵 정렬이 모두 빨랐고, First가 가장 빨랐다.
- 따라서 **값 비교 횟수가 적다고 실행시간이 반드시 짧은 것은 아니다.** 병합 정렬은 임시 배열을 할당하고 데이터를 병합 배열로 쓰고 다시 원래 배열로 복사해야 한다. 반면 퀵 정렬은 동일 배열에서 피벗을 기준으로 원소를 교환하며 분할하여, 메모리 복사·메모리 접근 패턴·함수 호출 비용 등의 영향을 다르게 받는다.
- Random Pivot은 피벗 선택에 난수 연산이 추가되며, 분할 균형이 반드시 좋지는 않다. 이번 실험의 `n=20,000`에서 Random이 가장 많은 비교(356,007회)와 가장 긴 퀵 정렬 시간(1.129020ms)을 보였다.
- 단, 100회 평균이어도 CPU 부하, 캐시, 컴파일러 최적화에 따라 매우 짧은 실행시간은 달라진다. 특히 First와 Median-of-Three의 작은 차이를 **일반적으로 항상 더 빠르다는 법칙**으로 해석해서는 안 된다.

### 6.3. 메모리 사용량 차이

- `n=1,000`: 병합 정렬 **4,480B** / 퀵 First **1,128B**, Random **1,008B**, Median-of-Three **800B**로 계산되었다.
- `n=20,000`: 병합 정렬 **80,680B** / 퀵 First **1,368B**, Random **1,568B**, Median-of-Three **1,200B**로 계산되었다. 이 크기에서 병합의 추가 메모리 추정량은 Median-of-Three의 **약 67.2배**였다.
- 병합 정렬에는 `20,000 * sizeof(int) = 80,000B`의 임시 배열이 필수이고, 나머지 **680B**는 최상위 함수, 재귀 깊이 및 병합 도우미를 위한 프레임 모델로 계산된 값이다. 데이터 크기가 커질수록 **임시 배열이 선형 증가**하므로 전체 공간 사용량이 `O(n)` 경향을 보인다.
- 퀵 정렬은 병합용 `n` 크기 배열을 할당하지 않고 제자리 분할한다. 이번 무작위 입력에서는 스택 깊이가 상대적으로 작아 추가 메모리도 1~2KB 안팎이었다. 다만 **불균형 분할이 연속되면 퀵 정렬 재귀 깊이가 최대 `O(n)`까지 증가**하므로, 최악 추가 스택 공간도 `O(n)`이 될 수 있다.
- 세 퀵 정렬의 메모리 계산값이 서로 다른 이유는 **피벗 선택에 따른 재귀 깊이**가 다르고, Median-of-Three에는 피벗 중앙값 선택용 프레임 모델이 더해지기 때문이다. 비교 횟수가 적다고 재귀 깊이의 최댓값이 항상 작은 것은 아니다.

### 6.4. 퀵 정렬 피벗 선택 방식에 따른 차이

- **First Element**는 피벗 선택 시 데이터 비교가 없다. 이번 `n=20,000`에서는 Median-of-Three보다 비교가 **약 3.7% 많았지만 실행시간은 조금 짧았다**. 피벗 선택을 위한 추가 작업이 없기 때문일 가능성이 있다. 그러나 이미 정렬된 데이터 등에서는 편향된 분할로 최악 `O(n²)`이 쉽게 발생할 수 있다.
- **Random Pivot**은 고정된 첫 원소에만 의존하는 편향을 확률적으로 줄이지만, 균형 분할을 보장하지는 않는다. 이번 `n=2,000`에서는 퀵 정렬 중 비교 횟수가 가장 적었지만 `n=20,000`에서는 가장 많았다.
- **Median-of-Three**는 첫 번째·중간·마지막 세 값 중 중앙값을 골라 극단적 피벗을 줄이려는 방식이다. **6개 입력 크기 중 4개에서 퀵 정렬 최소 비교 횟수**를 기록했고, `n=20,000`에서는 Random보다 **약 10.8% 적게 비교**했다. 다만 중앙값 선정을 위한 추가 2~3회 비교를 포함하고 있으며, 작은 시간 차이는 실험 환경에 따라 바뀔 수 있다.
- 중복 값이 많을 때는 이번 코드의 2방향 Lomuto 분할에서 `<=` 조건 때문에 같은 값이 한쪽으로 몰릴 수 있다. 따라서 Random이나 Median-of-Three도 **최악 `O(n²)` 시간**을 이론적으로 피하지 못한다.

### 6.5. 시간 및 공간 복잡도 정리

| 알고리즘 | 최선 시간 | 평균 시간 | 최악 시간 | 추가 공간 |
|---|---|---|---|---|
| Merge Sort | `O(n log n)` | `O(n log n)` | `O(n log n)` | `O(n)` 임시 배열 + `O(log n)` 스택 → `O(n)` |
| Quick (First) | `O(n log n)` | `O(n log n)`* | `O(n²)` | 평균 `O(log n)` / 최악 `O(n)` 재귀 스택 |
| Quick (Random) | `O(n log n)` | 기대 `O(n log n)` | `O(n²)` | 기대 `O(log n)` / 최악 `O(n)` 재귀 스택 |
| Quick (Median3) | `O(n log n)` | 일반적인 무작위 입력에서 `O(n log n)` | `O(n²)` | 일반적인 무작위 입력에서 `O(log n)` / 최악 `O(n)` 재귀 스택 |

\* First Element의 평균 시간은 무작위 순열에 대한 평균을 뜻한다. 정렬된 배열 등 피벗에 불리한 입력에서는 평균적인 성능이 보장되지 않는다. 세 Quick 방식 모두 위 표의 공간 계산은 **본 과제에서 사용한 양쪽을 재귀 호출하는 구현**을 기준으로 한다.

### 6.6. 결론

이번 동일 데이터 실험에서는 **병합 정렬이 모든 데이터 크기에서 데이터 값 비교를 가장 적게** 수행하였다. 이는 두 정렬된 부분 배열을 규칙적으로 병합하여 비교 횟수가 안정적으로 늘어나는 구조와 관련이 있다. 반면 **실행시간은 퀵 정렬이 유리한 경우가 많았는데**, 병합 정렬의 별도 배열 쓰기·복사·할당 비용과 퀵 정렬의 제자리 분할 특성이 영향을 미친 것으로 해석된다. 추가 공간에서는 **퀵 정렬이 유리**했다. 다만 퀵 정렬은 피벗에 따른 재귀 깊이 및 비교 횟수 변화가 크고, 최악 시간·스택 공간이 나빠질 수 있다. 즉, 정렬 알고리즘의 성능은 **비교 횟수뿐 아니라 데이터 이동, 메모리 접근, 피벗 선택 및 재귀 호출 구조**까지 함께 고려해야 한다.
