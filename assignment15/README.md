# 과제 15 — 퀵 정렬과 AVL 트리 정렬의 성능 비교

## 1. 과제 목적 및 제출물

**동일한 무작위 정수 데이터**를 퀵 정렬(정렬 배열 유지)과 AVL 트리(균형 탐색 트리 유지)로 처리한 후, 초기 크기의 20%에 해당하는 **동일한 삽입·삭제 시퀀스**를 수행한다. **최초 정렬부터 최종 조작까지의 전체 과정**에서 시간, 정수 키 비교, 정수 키 복사·대입, 피크 메모리를 비교한다. 자료구조의 **구조적 차이**가 실제 측정 결과에 미치는 영향도 분석한다.

제출물: `main.c`, `README.md` **두 파일**. 별도 `sample_output.txt`나 외부 라이브러리는 필요하지 않다.

### 컴파일 및 실행

macOS / Linux (최적화 빌드 예시; 본 문서의 Windows 실측과는 빌드 조건이 다름):

```bash
gcc -std=c11 -O2 -Wall -Wextra -pedantic main.c -o main
./main
```

기존 과제에서 사용하던 `gcc main.c -o main && ./main`도 가능하지만 **최적화 옵션이 다르면 실행시간은 달라질 수 있다.** 비교·이동 횟수와 자료구조 크기는 같은 환경·정의에서 일정하다.

Windows + MinGW GCC (아래 실측에 사용한 명령):

```powershell
gcc main.c -o main
.\main
```

경고를 추가해 확인하려면 `gcc -std=c11 -Wall -Wextra -pedantic main.c -o main`으로 컴파일할 수 있다. 다만 `-O2`와 같은 최적화 옵션을 추가하면 이 문서의 Windows 실측 시간과 달라질 수 있다.

계산 결과가 불일치하면 오류 메시지를 표시하고 비정상 종료한다. 모든 검증을 통과하면 `ALL TESTS PASSED`를 출력한다.

| 삭제 규칙 | 값이 있으면 **원소 한 개만 삭제**; 없으면 아무것도 삭제하지 않음 |
| 결과 검사 | 매 조작 후 **정렬 배열과 AVL 중위 순회 결과가 완전히 동일**해야 함 |

### 퀵 정렬 방식 — 이전 과제 14를 계승

이전 과제의 `Quick (Median3)` 분기에서 사용한 **Median-of-Three(첫 번째·중간·마지막 값 중 중앙값) 피벗** 선택 및 **Lomuto 분할**을 유지했다. 이번 과제에서 추가된 것은 `Metrics`를 통한 **정수 값 이동 집계**와 정렬 이후의 **배열 선형 삽입·삭제**이다. 기존 과제의 랜덤 피벗(`PIVOT_SEED = 20261212`)은 **이번에 선택한 방식이 아니므로 사용하지 않는다**.

- 중앙값 피벗 선택 과정에서 수행하는 **데이터 값 비교**도 센다.
- 원래 Lomuto 구현과 동일하게 제자리 스왑(self-swap)도 수행하므로, 실제 실행된 스왑의 정수 대입 3회를 모두 센다.
- 정렬 후 삽입은 **선형 탐색**으로 위치를 찾고 뒤의 원소를 오른쪽으로 한 칸씩 민다. 중복값은 같은 값 뒤에 삽입한다.
- 정렬 후 삭제는 **선형 탐색**으로 첫 번째 일치값을 찾고 뒤의 원소를 왼쪽으로 한 칸씩 당긴다. 정렬된 배열이므로 현재 값이 대상보다 커지면 탐색을 중단한다.

### AVL 트리 방식

- 정수를 하나씩 AVL 트리에 삽입하며 루트부터 키를 비교한다. 높이 차가 2 이상이면 **LL, RR, LR, RL 회전**으로 균형을 복구한다.
- 중복값은 별도 노드를 만들지 않고 **각 노드의 `count` 필드로 개수**를 관리한다.
- 삭제할 노드의 `count > 1`이면 `count`만 1 감소한다. 나머지 경우 BST 방식으로 노드를 제거한 뒤 재균형화한다.
- 자식이 두 개인 노드의 삭제에서는 **중위 후속자 키와 후속자의 전체 중복 개수를 옮기고**, 원래 후속자 노드 자체를 제거한다. 따라서 **서로 다른 키는 하나의 노드에만** 저장된다.
- **중위 순회**로 오름차순과 중복 원소의 개수를 확인한다.

## 3. 성능 측정 정의와 공정성

| 지표 | 공통 측정 기준 |
|---|---|
| **총 수행시간** | 최초 **정렬 시작**부터 마지막 삽입·삭제까지. `CLOCK_MONOTONIC`(macOS/Linux), `QueryPerformanceCounter`(Windows)의 **경과시간(ms)**. 각 크기당 **1회 전체 실행**을 측정하며, 정렬 단계와 조작 단계도 분리 집계 |
| **비교 횟수** | 두 **정수 데이터 키**의 관계를 판정하는 비교 한 번 = 1. 퀵 정렬 피벗 선정·분할, 배열 위치 탐색, AVL 삽입·삭제 키 탐색을 포함. 인덱스 범위·높이·균형 인수 등 제어용 비교는 제외 |
| **데이터 이동 횟수** | **정수 키 값**의 명시적인 대입·복사 1회 = 1. `swap`은 임시 변수까지 3회, 퀵 정렬 피벗을 임시 변수로 복사할 때 1회, 배열 밀기/당기기와 삽입 위치 기록은 각각 1회, AVL의 신규 노드 키 기록·삭제 중 후속자 키 덮어쓰기도 각각 1회 |
| **이동 집계 제외** | 입력 배열 초기화 `memcpy`, 함수 인자 전달, 정수 외 메타데이터(`height`, `count`), 포인터 연결 변경·회전의 포인터 대입, 메모리 관리 내부 이동, 검증용 배열 복사 |
| **메모리 사용량** | **작업 자료구조의 최대 점유 추정치(Bytes)**. 퀵: 확보한 배열 용량 `(n + n/5) × sizeof(int)` + 최대 재귀 깊이 × `sizeof(QuickFrameModel)`. AVL: 동시에 살아 있는 노드 수 × `sizeof(AVLNode)` + 최대 재귀 깊이 × `sizeof(AvlFrameModel)` |

**중요: 메모리 값은 운영체제의 실제 RSS 피크가 아니라 코드에서 정의한 일관된 ‘소스 수준 모델 추정치’이다.** 컴파일러가 생성한 실제 스택 프레임의 패딩·레지스터 저장, `malloc` 관리 오버헤드는 측정하지 않으며, 실행 환경·자료형 크기에 따라 바이트 값이 달라질 수 있다. 초기 원본 데이터, 미리 생성한 **공통 연산 목록**, 결과 검증용 임시 배열은 두 방식에 똑같이 제공되는 벤치마크 입력/검증 기반이므로 **양쪽 메모리 지표에서 공통으로 제외**한다. 퀵 정렬의 배열은 가장 많은 삽입 경우에도 재할당이 필요 없도록 미리 `n+n/5`개만큼 확보한다. AVL 노드는 필요할 때 할당하고 삭제 시 해제한다.

### 시간에 포함·제외되는 작업

- **포함:** 퀵 정렬 / AVL 초기 구축, 실제 삽입·삭제 및 재균형화, 데이터 비교·이동 집계.
- **제외:** 입력·피벗과 관계없는 조작 시퀀스 난수 생성, 출력, 초기 배열 복사, 정렬 결과 검증·전체 검증 재실행, 정리용 메모리 해제.
- **검증 방법:** 측정이 끝난 뒤 별도의 재실행에서 `qsort`로 만든 기준 배열과 AVL 트리를 생성하고 **0번째 상태와 모든 1..n/5번째 조작 직후**를 비교한다. 중위 순회 결과, 노드 중복 개수, 엄격한 BST 순서, 노드 높이, 균형 인수(±1 이내), 최종 원소 수를 모두 검사한다. 검증은 실제 벤치마크 구간 바깥이므로 시간·이동 횟수에 영향을 주지 않는다.

## 5. 측정 결과 비교·분석

### 5.1 총 수행시간·비교 횟수

- **초기 정렬만** 비교하면 n=20,000에서 퀵 정렬은 **3.169 ms**, AVL 구축은 **9.228 ms**로 퀵 정렬이 더 빨랐다. 연속된 배열 내 분할·교환은 트리 노드별 할당·연결보다 캐시 지역성과 메모리 관리 측면에서 유리할 수 있기 때문이다.
- **삽입·삭제 단계**에서는 n=20,000에서 퀵 기반 배열이 **219.018 ms**, AVL이 **1.724 ms**로 큰 차이가 발생했다. 정렬 배열은 매 연산의 삽입 위치나 삭제할 값을 선형 탐색하고 원소를 다수 이동한다. AVL은 높이를 `O(log n)`으로 유지하므로 반복 갱신에 유리하다.
- 따라서 **총 수행시간**은 n=20,000에서 퀵 기반 배열 **222.187 ms**, AVL **10.952 ms**, 즉 **2차 실행에서 AVL이 약 20.3배 빠르게** 측정되었다. 1차 실행에서도 퀵 **232.100 ms**, AVL **13.242 ms**로 AVL이 더 빨랐다. n=1,000에서도 2차 실행은 **0.764 / 0.416 ms**였으며, 작은 값의 시간 차이는 시스템 변동을 고려해 해석해야 한다.
- **전체 정수 키 비교 횟수**는 n=20,000에서 퀵 배열 **41,949,614회**, AVL **316,433회**로 약 **133배 차이**다. 갱신 단계의 비교만 보면 각각 **41,631,994회**, **57,182회**로, 정렬 자체보다 **반복 조작 시 선형 탐색 비용 누적**이 전체 차이를 만든다.
- 데이터 크기가 증가할수록 2차 전체 실행시간은 퀵 **0.764 → 222.187 ms**(약 **291배**), AVL **0.416 → 10.952 ms**(약 **26배**)로 늘었다. 서로 다른 자료구조의 증가 추세를 보여 주지만, 각 크기의 단일 시간 실측에는 잡음이 포함된다.

### 5.2 정렬·삽입·삭제 단계의 데이터 이동 비교

아래 표의 단위는 **정수 키 복사·대입 횟수**다. `정렬 + 삽입 + 삭제 = 총 데이터 이동 횟수`를 만족한다.

| n | 구분 | 정렬 이동 | 삽입 이동 | 삭제 이동 | 총 이동 |
|---:|---|---:|---:|---:|---:|
| 1,000 | Quick | 17,388 | 52,645 | 64 | 70,097 |
| 1,000 | AVL | 996 | 98 | 0 | 1,094 |
| 2,000 | Quick | 39,888 | 197,927 | 8,049 | 245,864 |
| 2,000 | AVL | 1,982 | 182 | 2 | 2,166 |
| 4,000 | Quick | 88,398 | 802,308 | 52,297 | 943,003 |
| 4,000 | AVL | 3,928 | 358 | 10 | 4,296 |
| 8,000 | Quick | 199,896 | 3,493,604 | 329,730 | 4,023,230 |
| 8,000 | AVL | 7,704 | 730 | 33 | 8,467 |
| 16,000 | Quick | 412,414 | 13,342,408 | 1,877,478 | 15,632,300 |
| 16,000 | AVL | 14,823 | 1,323 | 91 | 16,237 |
| 20,000 | Quick | 553,500 | 20,411,945 | 3,791,958 | 24,757,403 |
| 20,000 | AVL | 18,158 | 1,608 | 136 | 19,902 |

20,000개에서 **삽입·삭제 이동 합계**는 배열 **24,203,903회**, AVL **1,744회**였다. 배열은 새 값 하나만 삽입해도 삽입 지점 뒤의 많은 정수를 실제로 옮겨야 하고, 삭제에 성공하면 삭제 지점 뒤의 값을 모두 당긴다. AVL은 **노드 포인터만 변경되는 회전**과 **중복 개수만 증가·감소하는 조작**에서는 정수 키 이동이 추가되지 않는다. 따라서 AVL의 **데이터 이동이 거의 발생하지 않는 것**은 누락이 아니라 이 과제의 ‘포인터 변경 제외’ 정의에 따른 결과다.

### 5.3 메모리 사용량

| n | 퀵 기반 배열 (Bytes) | AVL 트리 (Bytes) |
|---:|---:|---:|
| 1,000 | 6,024 | 44,256 |
| 2,000 | 10,968 | 86,904 |
| 4,000 | 20,784 | 171,272 |
| 8,000 | 39,912 | 335,040 |
| 16,000 | 78,528 | 637,648 |
| 20,000 | 97,944 | 777,816 |

20,000개에서 AVL의 메모리 추정치는 배열보다 약 **7.9배** 컸다. 배열은 연속된 `int` 저장 공간과 재귀 호출 스택만 필요하다. AVL은 각 노드가 정수 키 외에도 **중복 개수, 높이, 좌·우 자식 포인터**를 보관하고 개별 메모리 할당을 수행하기 때문이다. 다만 AVL의 중복값은 같은 노드의 `count`에 누적하므로, 총 데이터 수와 노드 수가 항상 같지는 않다. 두 방법 모두 저장하는 키 개수에 비례하는 **`O(n)` 수준의 공간**을 사용하지만 **상수 계수**가 다르다. 실제 프로세스 메모리는 `malloc` 오버헤드 등의 영향으로 표보다 커질 수 있다.

### 5.4 데이터 크기가 증가하면 어떻게 달라지는가?

초기 크기가 1,000개에서 20,000개로 **20배** 증가하는 동안, 조작 횟수 역시 200회에서 4,000회로 20배 증가했다. 퀵 기반 배열의 전체 비교 횟수는 **115,230 → 41,949,614회(약 364배)**, AVL은 **10,772 → 316,433회(약 29배)** 증가했다. 퀵 정렬 자체의 평균 비교 비용은 `O(n log n)`이지만, 이후 **조작 횟수가 `0.2n`번**이고 각 조작 위치 탐색이 평균 `O(n)`이므로 조작 전체의 비용은 대략 **`O(n²)`**이다. AVL에서는 삽입·삭제 각각의 검색·재균형이 대체로 **`O(log n)`**이므로, 전체 초기 구축과 연산의 비용은 **`O(n log n)`**으로 성장한다.

참고로 조작 난수는 `0..99999`에서 무작위로 추출한다. 실제 성공 삭제 횟수는 n=1,000에서 **1회**, n=20,000에서 **374회**였다. 20,000개 경우 삽입 **1,976회**, 삭제 요청 **2,024회**, 그중 실패한 삭제가 **1,650회**다. 삭제가 실패해도 대상 존재 여부를 확인하는 **탐색 비용은 발생**하지만 데이터 이동은 없다. 이 실험은 **과제에서 지정한 난수 규칙 그대로 수행한 결과**로, 삭제가 항상 성공하는 일반화된 환경을 나타내지는 않는다.

### 5.5 삽입·삭제가 반복되는 환경에서 더 유리한 방식

이 실험의 조건(동일 초기 데이터에 초기 크기의 20%만큼 삽입·삭제 반복)에서는 **AVL 트리가 총 수행시간·비교 횟수·데이터 이동 횟수에서 더 유리했다.** AVL은 균형을 유지하므로 트리 높이가 작게 유지되고, 삽입·삭제 시 배열의 원소처럼 대량으로 이동하지 않기 때문이다. 반면 AVL은 **노드/포인터/높이/중복 개수의 추가 저장 공간**이 필요하고 할당·해제 비용도 발생한다.

따라서 **한 번 정렬한 뒤 읽기 위주**인 상황에서는 **배열 + 퀵 정렬**이 메모리·캐시 지역성·순차 접근 측면에서 유리할 수 있다. **정렬 상태를 유지하면서 삽입·삭제가 계속 발생**하는 상황이라면 **AVL**이 일반적으로 적합하다. 구조적 차이가 단순 정렬 속도보다 **조작이 누적되는 전체 처리 비용**에 큰 영향을 미쳤다는 것이 이번 과제의 핵심 결과다.
