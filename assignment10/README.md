# 과제 10: 정렬 알고리즘의 성능 및 안정성 비교

## 1. 프로그램 개요

10,000개의 `(Key 1, Key 2)` 레코드를 생성한 뒤, **Key 1만 기준으로 오름차순 정렬**하는 선택 정렬, 일반 버블 정렬, 조기 종료 버블 정렬, 삽입 정렬을 C 언어로 직접 구현했다. 무작위 데이터에 대하여 **100회** 실험을 수행하고, 같은 원본 데이터를 이용해 이미 정렬된 상태·역순 정렬된 상태·일부 정렬된 상태를 추가로 실험했다. 별도의 중복 키 데이터를 사용하여 안정성도 확인했다.

- 데이터 수: **10,000개**
- 무작위 반복: **100회**
- 키 범위: 두 키 모두 **0~1,000,000(양 끝 포함)**
- 시드: **20261026** (`./assignment10 다른양의시드`로 변경 가능)
- 언어: **C11**
- 소스: `main.c`
- 실제 실행 결과: 이 README의 **9절에 터미널 출력 원문 전체를 그대로 포함**한다.
- 진행 상황: 10회 단위의 완료 메시지를 표준 오류(`stderr`)에 출력한다. 9절에는 이 진행 메시지를 포함하여 Mac 터미널에서 확인한 전체 실행 결과를 실었다.
- 정렬 결과 검증: **100회 실험 및 모든 입력 상태에서 PASS**

한 개의 데이터는 `Record { int key1; int key2; int original_index; }`로 관리한다. `original_index`는 최초 입력 순서를 기록하는 값으로 **정렬 조건에는 사용하지 않는다**. 세 필드는 구조체 복사·교환 시 항상 함께 이동한다. 두 키는 난수 생성기를 독립적으로 두 번 호출하여 생성하며, 중복 값이 나올 수 있다.

## 2. 실행 방법

### macOS / Linux (gcc)

```bash
gcc -std=c11 -O3 -Wall -Wextra -Wpedantic main.c -o assignment10
./assignment10
```

시드 변경 예시(양의 정수):

```bash
./assignment10 12345
```

**빠른 기능 점검용(정식 100회 실험 대체 불가):** `gcc -std=c11 -O3 -DDEFAULT_TRIALS=1 main.c -o assignment10`으로 빌드하면 한 회만 실행한다. 이때 출력의 반복 횟수도 1회로 표시된다. 정식 제출 결과는 위의 기본 빌드(100회)를 사용한다.

### Windows (MinGW-w64 GCC, PowerShell)

```powershell
gcc -std=c11 -O3 -Wall -Wextra -Wpedantic main.c -o assignment10.exe
.\assignment10.exe
```

참고: 기본 실행은 10,000개 데이터에 대한 100회 반복으로 계산량이 많다. 소스의 `DEFAULT_TRIALS` 기본값은 **100**이며, 간단한 기능 확인에 한해서 `gcc -DDEFAULT_TRIALS=1 ...`처럼 컴파일 시 임시 변경할 수 있다. **이 README의 수치는 100회 정식 실행으로 측정했다.**

## 3. 실험 설계 및 측정 기준

### 3.1 동일 데이터로 공정하게 비교

무작위 데이터 100회 실험에서는 매 회차에 새로운 원본 레코드 10,000개를 생성한 다음 각 알고리즘이 실행되기 직전에 `memcpy`로 같은 원본을 복사한다. **복사 및 시험 데이터 생성 비용은 측정하지 않는다.** 일반 버블과 조기 종료 버블에도 같은 원본을 입력한다.

100회 실험 이후에는 **100번째 무작위 원본** 하나를 기준으로 입력 상태별 실험 자료를 생성한다. 따라서 정렬됨·역순·일부 정렬됨 세 상태 모두 같은 레코드 집합을 사용한다. 데이터 준비 과정의 정렬 및 교환은 성능 통계에 포함하지 않는다. 정렬 상태를 만들기 위한 준비 정렬도 직접 작성한 삽입 정렬로 수행했다. 정렬 알고리즘을 라이브러리 정렬 함수로 대체하지 않았다.

### 3.2 숫자 비교 횟수

오직 `key1`의 크기를 **정렬 순서 결정을 위해 실제 비교한 횟수**만 센다. 반복문 종료 조건 및 인덱스 비교는 제외하며, `key2`나 `original_index`를 정렬 판단에 사용하지 않는다.

### 3.3 데이터 이동 횟수

하나의 **Record 전체**를 임시 변수나 배열의 다른 위치에 복사·대입할 때마다 **1회**로 계산한다.

- 선택 정렬 / 버블 정렬: 서로 다른 위치 두 레코드를 임시 변수로 교환하면 **3회**. 선택 정렬에서 자기 자신과의 불필요한 교환은 하지 않으므로 **0회**이다.
- 삽입 정렬: `current = data[i]` **1회**, 배열의 한 칸 오른쪽 이동 **각 1회**, `data[j] = current` **1회**. 이미 올바른 위치에 있어도 임시 변수 저장 및 최종 대입이 발생하여 해당 단계에서 **2회**로 기록한다.
- 측정에는 원본 배열 복사, 테스트 데이터 준비, 인덱스 변경, 비교만 하는 작업이 포함되지 않는다.

모든 카운터에는 `uint64_t`를 사용한다(100회의 총합이 32비트 정수 범위를 초과할 수 있기 때문).

### 3.4 정렬 정확성 확인

결과 배열에서 `key1`이 **비내림차순**인지 확인할 뿐 아니라, `original_index`가 중복·누락되지 않았는지, 원본의 **두 키가 그대로 보존**되었는지 확인한다. 즉 `PASS`는 순서뿐 아니라 전체 레코드의 유실·변형도 없다는 의미이다.

**실험 결과 분석:** 선택 정렬은 남아 있는 구간 전체를 매번 탐색하기 때문에 데이터 분포와 관계없이 회차당 정확히 `10000 × 9999 / 2 = 49,995,000`회의 비교를 수행했다. 일반 버블 정렬도 모든 순회를 생략 없이 수행하므로 동일하게 49,995,000회 비교했다. 반면 버블 정렬은 역전된 인접 데이터마다 구조체를 **세 번 대입**해야 하므로 무작위 데이터에서 평균 약 7,499만 회의 이동이 발생했다. 선택 정렬은 위치당 많아야 한 번만 교환하므로 평균 약 3만 회 이동으로 상대적으로 적었다.

삽입 정렬은 앞쪽에 이미 정렬된 구간이 만들어지며, 삽입 위치를 찾은 순간 비교를 중단한다. 무작위 입력에서 비교가 평균 **25,007,167.44회**로, 고정된 비교 횟수를 가지는 선택 정렬·일반 버블 정렬의 약 절반이었다. 데이터 이동도 일반 버블보다 적었지만 선택 정렬보다는 많았다.

## 5. 일반 버블 정렬과 조기 종료 버블 정렬

일반 버블 정렬은 `n-1`번의 순회를 끝까지 수행한다. 조기 종료 버블 정렬은 한 순회에서 **교환이 0회**이면 배열이 이미 정렬되었다고 판단해 중단한다. 두 코드의 비교 및 교환 동작은 종료 조건을 제외하고 같다.

- **무작위 데이터 100회:** 일반 버블 `4,999,500,000회`, 조기 종료 버블 `4,998,648,314회`. **총 851,686회, 평균 8,516.86회**의 비교가 줄었다. 감소율은 약 **0.017%**로 크지 않다.
- **이미 정렬된 입력:** 일반 버블 `49,995,000회`, 조기 종료 버블 `9,999회`. 첫 번째 순회에서 교환이 발생하지 않아 바로 종료한 결과, **49,985,001회**의 비교를 절약했다.
- **역순 입력:** 두 방식 모두 `49,995,000회`. 역순에서는 거의 매 단계에 교환이 발생하므로 조기 종료의 이점이 없었다.
- **일부 정렬된 입력:** 일반 버블 `49,995,000회`, 조기 종료 버블 `49,864,695회`로 **130,305회** 감소했다. 일부가 정렬되어 있다는 사실만으로 반드시 이른 시점에 완전히 정렬되는 것은 아니다.

두 버블 정렬의 **이동 횟수는 네 입력 상태에서 모두 동일**하게 측정됐다. 같은 인접 교환을 수행하며 조기 종료는 더 이상 교환할 데이터가 없어졌을 때만 작동하기 때문이다.

### 6.1 이미 정렬된 데이터

선택 정렬의 비교는 여전히 `49,995,000회`로 변화가 없으나, 최소값이 이미 제자리에 있어 교환을 수행하지 않아 이동은 **0회**이다. 일반 버블도 이미 순서가 맞아 이동은 0회이지만 전체 순회를 수행하므로 비교가 여전히 많다. 조기 종료 버블은 **9,999회**의 첫 순회만 수행했다.

삽입 정렬은 이전 키보다 더 작은 데이터가 발견되지 않아 각 원소를 처리할 때마다 **1회 비교**만 하여 총 **9,999회** 비교한다. 하지만 구현에서 `current` 임시 저장과 최종 대입을 각각 1회로 세므로 **19,998회** 이동이 기록된다. 이는 이미 정렬된 데이터에서도 알고리즘 구현에 따라 이동 횟수가 0이 아닐 수 있음을 보여준다.

### 6.2 역순 정렬된 데이터

버블 정렬은 역전된 인접 쌍을 반복적으로 교환하여 **149,984,841회** 이동으로 증가했다. 무작위 데이터 평균 이동량의 약 2배이다. 삽입 정렬도 새 원소가 대부분 앞쪽으로 가야 하므로 **49,995,000회** 비교와 **50,014,945회** 이동이 발생했다. 입력에 같은 Key 1이 존재할 수 있어 `>` 방식은 동등한 키를 서로 밀지 않으므로, 이동 수가 모든 키가 서로 다를 때의 이론적 최댓값과 조금 다르다.

선택 정렬은 역순에서도 비교가 변하지 않으며, **15,081회** 이동했다. 선택 정렬의 이동 수는 단순한 역전 쌍 수보다 각 단계의 최소값 위치 및 실제 교환 발생 여부에 영향을 받기 때문이다.

### 6.3 일부 정렬된 데이터와 AI 활용

**AI(ChatGPT)를 활용하여** 부분 정렬 데이터의 생성 방법(국소 구간 섞기, 무작위 위치 교환, 일부 구간만 정렬)을 검토했다. 실험에서는 일부만 흐트러뜨린 입력이 삽입 정렬에 어떤 영향을 주는지 확인하기 위해 **정렬된 배열에서 전체 원소의 10%에 해당하는 서로 다른 위치 1,000개를 선택하고, 이를 서로 겹치지 않는 500쌍으로 교환**하는 방식을 설계하여 구현했다. 위치는 Fisher–Yates 방식으로 중복 없이 무작위 선택했다. 따라서 9,000개의 위치는 교란 대상으로 선택되지 않지만, 다른 위치로 이동한 데이터가 전역 순서에 영향을 줄 수 있다. `Key 1`이 동일한 원소 쌍도 교환할 수 있으므로 'Key 1이 다른 값으로 바뀐 위치가 반드시 1,000개'라는 뜻은 아니다. 교란은 `Key 1`만 바꾸는 것이 아니라 **구조체 전체를 교환**한다.

실측 결과 삽입 정렬은 **3,113,416회 비교 / 3,123,415회 이동**으로, 무작위 데이터 100회 평균(약 2,501만 회)에 비해 모두 약 **87.5% 감소**했다. 상당수 원소가 원래 정렬된 위치 근처에 있어 왼쪽으로 길게 이동할 필요가 줄었기 때문이다. 일반 버블은 전체 반복 구조 때문에 여전히 **49,995,000회** 비교했다. 조기 종료 버블은 **49,864,695회** 비교로 소폭 감소했다. 일부 위치를 멀리 교환하면 뒤쪽의 작은 원소가 앞쪽으로 이동하기까지 여러 순회가 필요하므로, 부분 정렬 상태라고 해도 조기 종료가 대폭 일어나지는 않는다.

이 실험은 **실제 C 프로그램에서 생성한 데이터와 측정값**을 사용한 것이며, AI가 비교·이동 횟수를 추정해서 채운 것이 아니다. 같은 시드를 사용하면 부분 교란 위치 및 모든 결과를 재현할 수 있다.

## 7. 정렬 알고리즘 안정성 검증

### 7.1 검증 데이터 및 방법

일부 무작위 실험에서는 중복 키가 드물 수 있으므로, 다음처럼 **Key 1이 반복되는 6개 레코드**를 별도로 준비했다. 괄호에는 `(Key 1, Key 2)`를, `id`에는 **원래 입력 순서**를 표시한다.

```text
원본 순서:
id=0 (2,100)
id=1 (2,200)
id=2 (1,300)
id=3 (3,400)
id=4 (2,500)
id=5 (1,600)
```

키가 1인 원본 순서는 `[2,5]`, 키가 2인 원본 순서는 `[0,1,4]`이다. 정렬한 뒤 같은 키의 레코드에 대해 `original_index`가 증가하는지 검사했다. 이 값은 오직 **검증**에 사용하고 정렬 시에는 비교하지 않는다.

### 7.2 실제 정렬 출력 비교

| 알고리즘 | 정렬 결과의 원래 ID 순서 | 안정성 |
|---|---|---|
| 선택 정렬 | `2, 5, 0, 4, 1, 3` | **UNSTABLE** |
| 일반 버블 정렬 | `2, 5, 0, 1, 4, 3` | **STABLE** |
| 삽입 정렬 (`>`) | `2, 5, 0, 1, 4, 3` | **STABLE** |
| 삽입 정렬 (`>=`) | `5, 2, 4, 1, 0, 3` | **UNSTABLE** |

모든 결과는 **Key 1 오름차순 정렬 자체는 PASS**했다. 안정성은 정렬 정확성과 구별되는 특성이다.

### 7.3 왜 이런 차이가 발생했는가?

**선택 정렬:** 최솟값을 찾은 후 떨어진 위치의 레코드를 직접 교환한다. 앞쪽에 있던 같은 키의 레코드가 뒤로 밀려 상대 순서가 뒤집힐 수 있다. 실제로 Key 1이 2인 세 레코드의 원래 순서 `[0,1,4]`가 `[0,4,1]`로 바뀌었다. 따라서 이 구현은 **불안정 정렬**이다.

**버블 정렬:** 인접한 두 Key 1이 앞 `>` 뒤일 때에만 교환하며 같은 키끼리는 교환하지 않는다. 따라서 원래 순서 `[0,1,4]`가 유지되었다. **안정 정렬**이다. 조기 종료 옵션은 교환 조건을 바꾸지 않으므로 안정성도 동일하다.

**삽입 정렬 (`>`):** `data[j-1].key1 > current.key1`일 때만 기존 레코드를 오른쪽으로 밀어낸다. 같은 키를 만나면 더 이상 이동하지 않으므로 기존 동일 키의 뒤에 들어간다. 결과 `[0,1,4]`가 유지되어 **안정 정렬**이다.

**삽입 정렬 (`>=`):** `data[j-1].key1 >= current.key1`로 조건을 바꾸면 키가 같은 데이터까지 오른쪽으로 밀어낸다. 나중에 입력된 동등 키가 앞쪽에 놓이면서 Key 1이 2인 원본 순서 `[0,1,4]`가 `[4,1,0]`으로 뒤집혔고, Key 1이 1인 `[2,5]`도 `[5,2]`로 뒤집혔다. 따라서 **불안정 정렬**이다.

**결론:** 키 비교 연산자를 `>`에서 `>=`로 바꿔도 Key 1 기준 오름차순이라는 정렬의 정확성은 유지되지만, **동일 키끼리의 상대 순서는 달라질 수 있다.** 안정성까지 요구한다면 `>` 조건을 유지해야 한다.

## 8. 종합 분석 및 결론

| 알고리즘 | 비교 횟수의 특징 | 이동 횟수의 특징 | 안정성 |
|---|---|---|---|
| 선택 정렬 | 입력 상태와 무관하게 `n(n-1)/2` | 위치별 최대 1교환; 전반적으로 적음 | 불안정 |
| 일반 버블 | 입력 상태와 무관하게 `n(n-1)/2` | 역전된 인접 쌍마다 3회; 많음 | 안정 |
| 조기 종료 버블 | 완전히 정렬되면 빨리 종료 가능 | 일반 버블과 교환 횟수 동일 | 안정 |
| 삽입 (`>`) | 정렬된 입력에 매우 유리; 역순에서 최대 수준 | 이동해야 할 원소 수에 영향을 받음 | 안정 |

- **이미 정렬된 입력에서 유리한 알고리즘:** 조기 종료 버블과 삽입 정렬은 비교를 **9,999회**만 수행했다. 선택·일반 버블은 **49,995,000회**였다.
- **일부 정렬된 입력에서 유리한 알고리즘:** 본 실험에서 삽입 정렬은 비교 **3,113,416회**로 크게 감소했다. 선택·일반 버블은 초기 정렬 상태와 관계없이 비교 횟수가 고정된다.
- **역순 입력에서 불리한 알고리즘:** 버블 정렬은 매우 많은 인접 교환을 수행했다. 삽입 정렬도 비교와 이동이 늘어나지만 본 실험에서는 일반 버블보다 이동 횟수가 적었다.
- **이동 횟수를 줄이는 목적:** 선택 정렬은 비교 횟수는 많지만 이동 횟수가 작았다. 다만 안정성이 필요한 상황에는 그대로 사용하기 어렵다.
- **안정성이 중요한 목적:** 일반·조기 종료 버블 및 `>`를 사용하는 삽입 정렬은 동일 Key 1의 기존 순서를 보존했다. `>=`로 변경하면 삽입 정렬도 안정성을 잃을 수 있다.

**최종 판단:** 이번 실험에서는 **비교 횟수와 초기 정렬 상태 적응성 면에서 삽입 정렬 (`>`)이 유리**했으며, **이미 정렬된 배열에는 조기 종료 버블도 효과적**이었다. 반면 **이동 횟수만 중시하면 선택 정렬이 유리**할 수 있지만 안정성이 보장되지 않는다. 따라서 어떤 알고리즘이 '무조건 최고'라고 할 수 없으며, **초기 데이터의 정렬 정도, 비교 비용, 이동 비용, 안정성 필요 여부**를 함께 고려해야 한다.
